# 0023 · Device ownership and delivery-time run authority

2026-10-21 · Accepted engineering fix for the MVP context review (findings 1 and 3).

Before a browser engine is built, each activation verifies the stable person who owns its SQLite data. The public SDK boundary is `BrowserRuntime.authorize(database)`, checked every time and never sealed as a successful migration step. Refusal prevents engine creation, recovery and database serving. The app keeps a versioned bootstrap ownership singleton outside clearable synced rows, retains ownership through session expiry, and checks a localStorage mirror before a tab follows an existing leader. The mirror can constrain startup but cannot grant ownership of SQLite. A different principal triggers the existing cross-tab, exclusive device wipe before opening any retained collection. An expired session opens memory state with no engine; the same owner can recover the stored data after reauthentication or offline reload.

Old login-only identities and nonempty unowned stores have no stable proof of ownership. GitHub logins can be reassigned, so matching a login is insufficient: online activation coordinates a wipe; offline opening preserves the old data. All own-origin API requests from a tab and its worker bind their expected stable person id; the server rejects a cookie for another person. This closes the old-tab/outbox race during an account change. External requests carry no device header. Sign-out applies the same principal check before any revocation or cookie change; identity reads stay unbound. Both SQLite and IndexedDB wait for an authoritative leader receipt and current-session verification. An old leader's missing receipt settles this tab on memory after 30 seconds and stops its worker; late receipts never reopen its retained stores.

A queued agent issue write retains its original signed proof and renews it at delivery through the existing credential route. The server checks its signature, live original session, identical current person/session and identical run, then copies every claim except expiry. It never reconstructs a wider lineage or interprets the write as the person's press. The write itself sends the renewed bearer with cookies omitted. Revoked, forged or cross-account proofs are refused; transient failures use the existing outbox retry policy. Payload version 3 migrates version 2 without changing its operation, write id or proof. The existing idempotency boundary handles replay.

Libraries used: `@smthrs/platform-browser` for host activation and the shared SQLite service; `@smthrs/effect-tanstack-db` for collections, outbox delivery and versioned schema/payload migration; the existing Effect run-credential services and durable engine. No second worker loop or retry mechanism is added. Observability records activation outcome, credential renewal/refusal and device-principal refusal without identities, credentials or message content.

Tests cover retained owner across expiry/deletion, login renaming, legacy ambiguity, offline recovery, cross-account requests, exact attenuation, original-session revocation and replay. The browser regressions cover expiry, draft recovery, account change across tabs and pending person writes. Execution receipts are recorded in the work note; tests listed here do not imply a passing unexecuted suite.


Cookie-authenticated application mutations require the expected-person header; missing bindings are refused before any write. This also applies to raw-cookie sign-out. A verified bearer retains its own principal and is exempt from the cookie-binding requirement. Identity reads and OAuth bootstrap remain unbound. Thus a pre-deploy tab cannot send an old queued body as the new cookie owner during the redirect before the new page's coordinated wipe; legacy tabs fail closed until reload. Real-cookie test clients state the expected stable identity explicitly.

An offline activation without stable ownership never adopts a principal in place. On reconnect, the host reads the session again; a verified signed-in response triggers the coordinated wipe and a fresh authorized boot before Auth publishes that session. Until teardown, requests remain sealed. A stable already-owned offline activation retains its existing recovery path.

Once the bootstrap owner exists, activation does not read the legacy auth collection. Collection registration and physical table creation are separate operations; an interrupted first navigation may leave only the registration. That incomplete collection cannot invalidate independent durable ownership. A regression preserves this state and checks successful same-owner activation.
