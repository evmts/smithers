# 0090 — A personal pinned message

Accepted 2026-10-23. Will's 14:24 request: keep a message at the top while discussing it.

A person pins any of their own or the agent's messages from its actions. One pin per person per conversation; another replaces it. Unpin works from either copy. The pinned copy sits outside the conversation's scrollport, reads the whole device collection, and follows streaming changes. Its height is bounded at every width, with its own scroll and a collapse toggle. Collapse is tab-local TanStack DB state. Controls use icons and accessible names, without explanatory copy.

Migration **0054** adds `message_pins`, keyed by conversation and person. Session identity fixes ownership; a caller never chooses another person. Electric filters the person's rows into a versioned TanStack DB device collection. Persisted local intents show offline, survive reload, and dispatch `chat/pin` or `chat/unpin` on the browser's durable engine. Timestamped unpin tombstones fence older retried pins; pin changes never affect branch sharing or anyone else's view.

Both flows are model-invocable. Without a message id, `chat/pin` resolves the previous completed agent answer before the invoking answer, so “pin that” does not pin its own acknowledgement. Explicit ids are checked against the conversation and branch read access. The server bounds request size and timestamps. Logs, traces and counters contain outcomes and status, never message text.

For agent calls the flow journals a server timestamp above the person's current pin timestamp before writing. An agent can therefore unpin after a device with a fast clock. The device supplies its persisted intent timestamp instead. A refused launch restores the synced pin and retains a failed intent with Retry; reload resumes only unfinished intents, and a late failure cannot erase a newer choice.

Queued and unsent questions can be pinned too, including the first question before the device knows its home conversation's server id. The versioned intent keeps that question's local text and expected answer id; the pinned query reads the full synced collection and keeps the local copy distinct even if another message has the same id. Taking back or discarding the original, and retrying a refused pin, retain that saved copy. Unpin remains available on the copy. The pin follows other devices after the matching question and answer are admitted. Until then `awaitAdmission` makes HTTP 425 retryable under the same durable flow; no app retry loop or extra queue. A newer personal pin or unpin settles an obsolete admission wait. Home intents use a stable local key and learn the server conversation id from the write receipt to acknowledge even an empty conversation.

Core placement: this is a conversation rendering and personal state primitive. The current public plugin interface offers shell slots but no per-message action or transcript scrollport context. This change extends the conversation's existing public frontend actions and flow catalog; it does not grant a first-party plugin a private host API. Catalog entries used: `@smthrs/flow`, `@smthrs/effect-tanstack-db`, `@smthrs/effect-electric`, and `@smthrs/ui`. No new library or runtime.

A queued message's Pin control captures `local=true`. Admission can remove its asking row before that rendered callback runs, after the previous intent has already been acknowledged. With neither a question nor a retained intent left, the action ignores the stale callback and leaves the synced pin unchanged. The real-service queued-question integration test exercises this case; removing the guard creates a new admission-waiting intent and fails its assertion.
