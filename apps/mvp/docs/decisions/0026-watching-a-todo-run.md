# 0026: Watching a TODO's run from the browser

Status: implemented (2026-10-21) for ruling TODO-3's watching, and steering (§6, 2026-10-21). Builds on [0016](0016-todos-and-the-stack.md) (the `todo` run), [0014](0014-flows-authoring-debugging-and-home-view.md) (the run page) and [0001](0001-electric-postgres-tanstack-db.md) (Electric).

A TODO starts a durable `todo` run on Cloudflare, one per attempt, `todo:<attempt id>`. Its journal lives in the engine's Postgres schema, `smithers_flows`, never on a device, and the browser's run page read only its own engine. Will asked that a running TODO link to its run, show that it is working, and let a person watch the agent (TODO-3).

## Decisions

1. **Working blinks; In review doesn't.** A Working TODO's state icon blinks slowly, one 2-second cycle, through `@smthrs/ui`'s `ItemStatus.live`, and holds steady under reduced motion through the house motion policy. In review links to its run too, steady: it waits on a person's merge, not on work.
2. **The TODO row names its run.** The writer records each attempt's execution id on its TODO, `todos.run_id`, in the transaction that records the attempt, and the row syncs to Members as before. Rejected: a route that resolves a TODO to its run (an extra round trip and a redirect before every link, and no link offline), and deriving the attempt id from the TODO (attempts are random UUIDs, and a derived id would need a hash in a pure view).
3. **The browser reads the engine's own read.** ChatApi serves `GET /api/remote-runs/<run id>` with `@smthrs/engine-store`'s `RunInspection` over the engine's schema, read-only, so the page gets the redaction, schema rendering, failure codes and 16 KiB cut a device's run page gets, and the browser decodes it with `BrowserEngine.Inspection`. Only a run a TODO's attempt started is served, to a Member or above. No journal is copied into the app's tables.
4. **Live from the engine's change feed, through Electric.** The engine keeps `flows_run_changes`, one row per run whose revision moves whenever the run's row is written. Correction, 2026-10-21: model turns and sandbox calls inside `todo/Implement` write a lossy journal trail within one attempt, not inner engine attempts. Run-store migration 1005 touches the run from journal inserts, durable or lossy, at most once per two seconds per run, so the feed moves during that attempt; other run state changes still advance it immediately. The tab follows that one row through ChatApi's shape proxy and reads the run again on each change, as it follows every synced table. Rejected: polling from the tab, a server loop, and a projection the run would write into the app's tables per event. Electric sets the table's replica identity itself, as owner of the engine's tables; the live end-to-end run on Cloudflare confirms it.
5. **No acts on a run on Cloudflare but Steer.** Stop, Retry and Resume act on this device's engine; a TODO's run stops when its TODO is dropped.
6. **Steering is the run's own notification queue.** A Member's message goes through a client flow, `run/steer`, and the device's outbox to `POST /api/remote-runs/<run id>/steers`, which admits it to the run's durable `NotificationQueue` (`@smthrs/notifications`) over the engine's journal, as a person's steer (`Notification.humanSteer`). The todo agent drains that queue at each turn boundary through `@smthrs/harness`'s `Notifications.layerForExecution()`, which names the execution it works in at each drain, so one registration serves every attempt. Each drain is keyed by the agent session as well as the boundary, since an action's retries and corrections number their turns from the start again. The page reads the message and its delivery from the run's journal: the queue's `Admitted` and `Promoted` records, and, since a promotion alone is no proof the turn ran, a cell call after it or the agent's answer, before it says Delivered. An agent's steer goes as its run (decision 0017 slice 0), never in the person's session. Admission is open while the run and its `todo/Implement` step haven't ended; a message that races the agent's last turn reads `Not delivered`. Rejected: an app table of messages read by an app-written source (a second durable queue beside the SDK's), a remote flow per message (an alarm and an engine build for one idempotent write), `Control.signal` or `DurableDeferred` (the agent loop drains at boundaries; it never waits on a signal), and a wake (the agent never parks on an event; a quota park drains its own boundaries when it resumes). Who: a Member or above, in person or through an agent acting for them (ruling FLOW-3). Where the composer lives is superseded by: everything is a plugin (design pending).

## Consequences

- One more synced column on `todos` (device store `todos` version 3: synced rows drop and sync again).
- Each run page a tab opens on a TODO's run keeps one Electric long poll for the life of the tab.
- A steer is one more writer of a run's journal beside its engine: ChatApi admits through a journal of its own over the engine's schema. Durable writes allocate their sequence under the engine's writer lock, so the two never collide.
- A message reaches the agent at its next turn boundary, not mid-turn: a long `sandbox/run` finishes first. A message delivered to one session of the agent's step is not handed to a later retry or correction of it.
- Admitting a message writes the run's journal; migration 1005 advances its change feed when progress is eligible, so another Member's open page can follow it during the same attempt. Inserts inside the two-second window coalesce; the next eligible insert advances the feed.
